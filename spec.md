# Спецификация: дозорный — OAuth2/OIDC identity provider для panos

**Пакет**: `panosiki/дозорный` (git-репозиторий
[github.com/Garius6/dozornyy](https://github.com/Garius6/dozornyy),
`pan`-управляемый)
**Создано**: 2026-08-21
**Статус**: Реализовано (v1) — US1/US2/US3, все FR-001..FR-012 и
SC-001..SC-006 закрыты, 62/62 e2e-проверки (`тест_дозорный.pns`,
реальный сокет). См. «Итоги реализации» в конце файла.
**Вход**: "Следующая задача — сделать аналог authentik на panos"

## Контекст

[Authentik](https://goauthentik.io/) — self-hosted identity provider:
OAuth2/OIDC provider, SAML IdP, LDAP/proxy outposts, визуальный
flow/stage/policy-движок, RBAC, admin SPA, event log. Полный аналог —
это годы работы одной командой; сессия явно ограничила скоуп v1 (см.
Assumptions) до того, что реально закрывает самый частый сценарий
("войти через X"): **OAuth2/OIDC provider** (Authorization Code + PKCE,
выдача id/access/refresh-токенов) **плюс admin REST/JSON API** для
управления пользователями/группами/клиентами — без SAML, без LDAP/proxy
outposts, без визуального flow-движка, без admin SPA (управление через
`curl`/скрипты).

`дозорный` строится НАД `быстряга` (не параллельная реализация HTTP-слоя)
— типизированные маршруты, авто-валидация/сериализация JSON, тот же
принцип, что `быстряга` унаследовала от `std/сеть/http.pns`. Хранилище —
`бд.*` (вендоренный SQLite, `panos/std/бд.pns`, уже существует).
Токены — `std/кодирование/jwt.pns` (HS256, HMAC-SHA256 через builtin
`крипто.*`, оба уже существуют — см. сессию, где они появились).

### Криптографические предпосылки (блокируют реализацию, не блокируют эту спеку) — ЗАКРЫТО

`криптография.sha256_base64url`/`pbkdf2_sha256_base64url` реализованы
в `panos/zig/core` (`vm.zig`) вместе с ТРЕТЬИМ builtin'ом, обнаруженным
уже В ПРОЦЕССЕ реализации и не предвиденным этой спекой заранее —
`криптография.случайные_байты_base64url` (CSPRNG, `std.Io.random`):
во всей VM panos не было НИ ОДНОГО источника криптографически стойкой
случайности до этого — `математика.*` (Lehmer/Park-Miller PRNG)
угадываем по построению, непригоден для authorization code/access/
refresh-токенов и соли пароля. Регрессия — `panos/fixtures/
crypto_fixture_main.pns` (SC-006).

`крипто.*` (`panos/zig/core`, builtin) на момент написания спеки
предоставляет ТОЛЬКО:
`hmac_sha256_base64url`/`base64url_кодировать`/`base64url_декодировать`/
`сравнить_константное_время`. Этого недостаточно для двух требований
ниже:

1. **PKCE (`code_challenge_method=S256`)** — RFC 7636 требует
   `code_challenge = BASE64URL(SHA256(code_verifier))` — ПЛОСКИЙ SHA256,
   не HMAC (нет отдельного ключа). Нужен новый builtin вида
   `крипто.sha256_base64url(текст) -> Строка` — небольшое, симметричное
   `hmac_sha256_base64url` дополнение (та же `std.crypto.hash.sha2.
   Sha256` из Zig stdlib, что уже используется для HMAC внутри).
2. **Хранение паролей** — HMAC-SHA256 (даже посоленный) — БЫСТРЫЙ хэш,
   не годится для паролей (offline brute-force). Нужна МЕДЛЕННАЯ
   key-derivation функция. PBKDF2-HMAC-SHA256 технически строится ПОВЕРХ
   уже существующего `hmac_sha256_base64url` (PBKDF2 — это просто N
   итераций HMAC с XOR), НО каждая итерация оперирует СЫРЫМИ байтами
   HMAC-дайджеста, а `крипто.*` сегодня отдаёт результат ТОЛЬКО как
   base64url-ТЕКСТ (`Строка` в panos обязана быть валидным UTF-8 — сырые
   байты HMAC-дайджеста почти никогда таковыми не являются, см.
   `docs/src/language/database.md`'s BLOB-обоснование для того же
   ограничения) — round-trip через `Строка` между итерациями невозможен.
   Нужен ЦЕЛЬНЫЙ native builtin `крипто.pbkdf2_sha256_base64url(пароль,
   соль, итерации) -> Строка`, считающий все итерации внутри Zig (сырые
   байты никогда не пересекают границу VM), отдающий наружу только
   финальный base64url-текст.

Обе функции — небольшие, чисто вычислительные (`native_only`, тот же
принцип, что у самого `крипто`), никакого нового вендоринга (снова
`std.crypto` из Zig stdlib). Это ПРЕДВАРИТЕЛЬНАЯ работа в `panos/zig/
core` перед тем, как реализация `дозорный` сможет закрыть FR-004/FR-010
ниже — зафиксировано здесь, чтобы не быть открытым при implementation
planning.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Authorization Code + PKCE, вход через дозорный (Priority: P1)

Стороннее приложение ("relying party", RP) хочет "войти через
дозорный". RP регистрирован заранее как OAuth2-клиент (FR-001) с
известным `redirect_uri`. Пользователь переходит по ссылке `/authorize
?...`, видит форму логина (если ещё не аутентифицирован в этой
сессии), вводит логин/пароль, видит экран согласия ("Приложение X
запрашивает доступ к: email, profile"), подтверждает — браузер
редиректится обратно на `redirect_uri` с `code`. RP обменивает `code`
на `id_token`/`access_token`/`refresh_token` через `POST /token`
(server-to-server, `client_id`+`client_secret`).

**Почему первый приоритет**: это и есть весь смысл identity provider'а
— без рабочего authorization code flow "дозорный" не отличается от
пустого HTTP-сервера.

**Independent Test**: зарегистрированный клиент, `GET /authorize?
response_type=code&client_id=...&redirect_uri=...&scope=openid+profile
&code_challenge=...&code_challenge_method=S256` → форма логина →
валидные креды → экран согласия → редирект с `code` на
`redirect_uri` → `POST /token` с `code`+`code_verifier`+
`client_secret` → `200` с `id_token` (валидный JWT, `sub`/`iss`/`aud`/
`exp` присутствуют, подпись проверяется `jwt.проверить` тем же
секретом, что клиент получил при регистрации).

**Acceptance Scenarios**:

1. **Given** незалогиненный браузер, **When** `GET /authorize` с
   валидными параметрами, **Then** ответ — форма логина (HTML), не
   редирект и не ошибка.
2. **Given** форма логина, **When** отправлен неверный пароль, **Then**
   форма логина повторно с сообщением об ошибке, сессия НЕ создаётся.
3. **Given** валидные креды, **When** логин успешен, **Then** экран
   согласия показывает ИМЯ приложения и запрошенные `scope`,
   пользователь может подтвердить или отклонить.
4. **Given** пользователь отклонил согласие, **When** редирект на
   `redirect_uri`, **Then** query-параметр `error=access_denied`, БЕЗ
   `code`.
5. **Given** согласие подтверждено, **When** редирект на
   `redirect_uri`, **Then** `code` присутствует, ОДНОРАЗОВЫЙ (повторный
   `POST /token` с тем же `code` — `400 invalid_grant`), с TTL (MUST
   истечь — см. FR-006).
6. **Given** корректный `code`+`code_verifier`, **When** `POST /token`
   с НЕВЕРНЫМ `code_verifier` (не соответствует `code_challenge`,
   отправленному на `/authorize`), **Then** `400 invalid_grant` — обмен
   МОЖЕТ провалиться (PKCE — защита от перехвата `code`).
7. **Given** валидный обмен, **When** `id_token` декодирован, **Then**
   `sub` — стабильный (не меняется между логинами ОДНОГО пользователя),
   `aud` == `client_id`, `iss` — базовый URL дозорного, `exp` в
   будущем.

### User Story 2 — Управление пользователями/группами/клиентами через admin API (Priority: P1)

Администратор (первый пользователь, созданный при инициализации — см.
FR-011) управляет системой через REST/JSON API — БЕЗ веб-интерфейса —
`curl`/скрипты. CRUD над пользователями, группами (пользователь состоит
в 0..N группах), OAuth2-клиентами (регистрация нового RP: `client_id`
чеканится сервером, `client_secret` возвращается РОВНО ОДИН раз при
создании).

**Почему первый приоритет**: без способа завести хотя бы одного
пользователя и одного OAuth2-клиента User Story 1 непроверяема — это
не "второстепенная фича", это предпосылка первой.

**Independent Test**: `POST /api/пользователи` с admin bearer-токеном
создаёт пользователя, `GET /api/пользователи/{ид}` возвращает его без
поля пароля (даже хэша), `POST /api/клиенты` создаёт OAuth2-клиента,
возвращает `client_secret` в ЭТОМ ответе и никогда больше.

**Acceptance Scenarios**:

1. **Given** admin bearer-токен, **When** `POST /api/пользователи`
   с `{"логин": "иван", "пароль": "..."}`, **Then** `201`, ответ НЕ
   содержит пароль/хэш пароля ни в каком виде.
2. **Given** тот же токен, **When** `GET /api/пользователи`, **Then**
   список без полей пароля.
3. **Given** admin bearer-токен, **When** `POST /api/клиенты` с
   `{"имя": "Моё приложение", "redirect_uri": "https://..."}`, **Then**
   `201` с `client_id`+`client_secret` в теле; повторный `GET
   /api/клиенты/{id}` НЕ возвращает `client_secret` (одноразовая
   выдача).
4. **Given** запрос БЕЗ admin bearer-токена (или с токеном обычного
   пользователя), **When** любой `/api/*`-запрос, **Then** `401`/`403`,
   не `500`.
5. **Given** группа создана и пользователь в неё добавлен, **When**
   `GET /api/пользователи/{ид}`, **Then** ответ включает список групп
   пользователя.

### User Story 3 — Refresh-токен продлевает сессию без повторного логина (Priority: P2)

RP, чей `access_token` истёк, вызывает `POST /token` с
`grant_type=refresh_token` — получает НОВЫЙ `access_token`/`id_token` И
новый `refresh_token` (ротация — старый немедленно инвалидируется).

**Почему второй приоритет**: работает поверх уже готового US1
(токены уже выдаются) — расширяет срок жизни сессии, не меняет сам
authorization code flow.

**Independent Test**: успешный обмен `code` → `refresh_token` →
`POST /token grant_type=refresh_token` с этим `refresh_token` → `200` с
НОВЫМИ `access_token`+`refresh_token`; повторный вызов СО СТАРЫМ
`refresh_token` → `400 invalid_grant` (ротация — одноразовость).

**Acceptance Scenarios**:

1. **Given** валидный `refresh_token`, **When** `POST /token
   grant_type=refresh_token`, **Then** `200`, `refresh_token` в ответе
   ОТЛИЧАЕТСЯ от переданного.
2. **Given** уже использованный (ротированный) `refresh_token`, **When**
   он переиспользован, **Then** `400 invalid_grant` — ОБА токена из
   этой цепочки (использованный и тот, что был выдан взамен) MUST быть
   инвалидированы (защита от кражи refresh-токена — повторное
   использование сигнализирует компрометацию).
3. **Given** `refresh_token` с истёкшим TTL, **When** обмен, **Then**
   `400 invalid_grant`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST хранить сущности `Пользователь` (логин,
  хэш пароля, email, активен/деактивирован), `Группа` (имя,
  пользователь состоит в 0..N групп через связующую таблицу), `Клиент`
  (OAuth2-клиент: `client_id`, хэш `client_secret`, имя, список
  разрешённых `redirect_uri`, список разрешённых `scope`) в SQLite
  через `бд.*`.
- **FR-002**: Пароли MUST храниться ТОЛЬКО как
  `крипто.pbkdf2_sha256_base64url(пароль, соль, итерации)` (новый
  builtin, см. "Криптографические предпосылки") с per-пользователь
  случайной солью — НИКОГДА в открытом виде и НИКОГДА через
  `hmac_sha256_base64url` напрямую (недостаточно медленно для паролей).
- **FR-003**: `GET /authorize` MUST принимать
  `response_type=code`+`client_id`+`redirect_uri`+`scope`+`state`+
  `code_challenge`+`code_challenge_method=S256` (RFC 6749 §4.1 + RFC
  7636) — MUST отклонить запрос (`400`, ДО показа формы логина) при
  неизвестном `client_id`, `redirect_uri`, не входящем в
  зарегистрированный список клиента, или отсутствующем/неподдерживаемом
  `code_challenge_method` (только `S256` — `plain` НЕ поддержан, тот же
  принцип, что современные провайдеры).
- **FR-004**: PKCE-проверка (`POST /token`) MUST сравнивать
  `крипто.sha256_base64url(code_verifier)` (новый builtin) с
  `code_challenge`, сохранённым при `/authorize`, через
  `крипто.сравнить_константное_время` (уже существует).
- **FR-005**: Успешный логин+согласие MUST выдавать `code` — случайный
  токен (не JWT — не несёт смысла клиенту), одноразовый, TTL ≤ 10 минут,
  привязанный к `client_id`+`redirect_uri`+`scope`+`code_challenge`+
  `sub` пользователя.
- **FR-006**: `POST /token grant_type=authorization_code` MUST
  проверить `client_secret` (аутентификация клиента — v1 поддерживает
  ТОЛЬКО confidential-клиентов, см. Assumptions), одноразовость и TTL
  `code`, PKCE (FR-004), совпадение `redirect_uri`, и MUST выдать
  `id_token`+`access_token`+`refresh_token` при успехе.
- **FR-007**: `id_token` MUST быть JWT (`std/кодирование/jwt.pns`,
  HS256, подписан `client_secret` клиента — симметрично: тот же секрет,
  которым клиент аутентифицируется на `/token`, используется как
  HMAC-ключ, что и позволяет клиенту локально верифицировать `id_token`
  без отдельного JWKS-эндпоинта — см. Assumptions про ограничение
  HS256-only). MUST содержать `iss`/`sub`/`aud`/`exp`/`iat` минимум;
  `email`/`profile`-claims — если `scope` их запрашивал.
- **FR-008**: `access_token` MUST быть непрозрачным случайным токеном
  (не JWT) — RP НЕ должен интроспектировать его локально; MUST
  проверяться через `GET /userinfo` (Bearer) MUST возвращать
  claims текущего пользователя по валидному `access_token`.
- **FR-009**: `refresh_token` MUST быть непрозрачным случайным токеном,
  MUST ротироваться при каждом использовании (FR US3 Acceptance
  Scenario 2 — повторное использование инвалидирует всю цепочку).
- **FR-010**: Система MUST предоставлять REST/JSON admin API
  (`/api/пользователи`, `/api/группы`, `/api/клиенты`, CRUD), защищённый
  отдельным admin-токеном (не обычный OAuth2 `access_token` — админ
  логинится через СВОЙ отдельный `POST /api/вход`, получает admin
  bearer-токен с более коротким TTL; ЛЮБОЙ `/api/*`-запрос без него —
  `401`).
- **FR-011**: При первом запуске (пустая БД — таблица пользователей
  пуста) система MUST создать ровно одного пользователя-администратора
  со случайно сгенерированным паролем, напечатанным В ЛОГ РОВНО ОДИН
  РАЗ при старте (тот же bootstrap-паттерн, что у большинства
  self-hosted систем — не хардкодить `admin`/`admin`).
- **FR-012**: `GET /.well-known/openid-configuration` MUST отдавать
  минимальный OIDC discovery document (`issuer`/
  `authorization_endpoint`/`token_endpoint`/`userinfo_endpoint`, БЕЗ
  `jwks_uri` — HS256-only, нет публичного JWKS, см. Assumptions).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Реальный e2e-тест (настоящий сокет) — полный
  authorization code + PKCE flow от `GET /authorize` до `POST /token`
  — `id_token` проходит `jwt.проверить` с секретом клиента.
- **SC-002**: Повторное использование ОДНОГО `code` — второй `POST
  /token` `400 invalid_grant`.
- **SC-003**: Неверный `code_verifier` — `POST /token` `400
  invalid_grant`, токены НЕ выданы.
- **SC-004**: `refresh_token` ротация — использование СТАРОГО
  (уже обменянного) `refresh_token` — `400 invalid_grant`.
- **SC-005**: Admin API — создание пользователя/группы/клиента через
  `curl`-эквивалентные e2e-тесты, ответы никогда не содержат
  пароль/хэш пароля/`client_secret` (кроме момента создания клиента).
- **SC-006**: `zig build test`/`conformance` (в `panos`) не задеты,
  ЕСЛИ новые `крипто.*`-builtin'ы (см. предпосылки) реализованы —
  регрессионный тест на них ДОЛЖЕН появиться в `panos/fixtures` тем же
  порядком, что `crypto_fixture_main.pns` для существующих.

## Assumptions

- **Скоуп v1** (явный выбор пользователя сессии): OAuth2/OIDC provider
  + admin REST/JSON API. ИСКЛЮЧЕНО из v1: SAML IdP, LDAP/proxy
  outposts, визуальный flow/stage/policy-движок (login+consent —
  ФИКСИРОВАННЫЙ, не настраиваемый через UI), admin SPA
  (веб-интерфейс) — управление ТОЛЬКО через `/api/*`, RBAC сверх
  "администратор либо обычный пользователь" (нет кастомных ролей/прав
  в v1).
- **Только confidential-клиенты** — v1 требует `client_secret` от
  КАЖДОГО клиента (в т.ч. с PKCE) — публичные клиенты (SPA/мобильные
  приложения без бэкенда, безопасно хранящие секрет) НЕ поддержаны.
  Прямое следствие HS256-only ограничения `крипто.*`/`jwt.pns` (нет
  RSA/ECDSA — нет способа подписать токен так, чтобы его МОГ
  верифицировать клиент, НЕ ЗНАЮЩИЙ секрета, то есть публичный клиент,
  без публичного JWKS-эндпоинта). PKCE в v1 — defense-in-depth поверх
  `client_secret` (защита от перехвата authorization code), не замена
  публичного клиента.
- **RS256/JWKS/публичные клиенты** — реалистичный follow-up (тот же
  паттерн, что "path-параметры остаются Строка" был отложен в спеке
  `быстряга`), НЕ в этой версии. Потребует НОВОГО крипто-примитива
  (RSA/ECDSA-подпись) — значительно больший объём работы в
  `panos/zig/core`, чем `sha256_base64url`/`pbkdf2_sha256_base64url`
  выше.
- **Single-tenant** — одна инсталляция дозорного обслуживает один набор
  пользователей/клиентов, нет мульти-тенантности/"realms" (Keycloak
  terminology) в v1.
- **Хранилище** — один файл SQLite (`бд.*`), без кластеризации/
  репликации — тот же выбор, что у `panos`'s собственного `бд`-builtin
  (v1 SQLite, без BLOB, см. `docs/src/language/database.md`).
- **Криптографические builtin'ы** (`криптография.sha256_base64url`,
  `криптография.pbkdf2_sha256_base64url` — модуль `крипто` переименован
  в `криптография` тем же коммитом) — ПРЕДПОСЫЛКА, реализована в
  `panos/zig/core` ДО начала реализации `дозорный` (см.
  "Криптографические предпосылки" в Контексте, статус ЗАКРЫТО). Не
  workaround (например, HMAC с фиксированным ключом вместо plain SHA256
  для PKCE, или один проход HMAC вместо PBKDF2 для паролей) — оба явно
  небезопасны и были отклонены заранее, а не "временное решение, пока
  не появится нормальное".
- **Название пакета "дозорный"** — выбор пользователя сессии (не
  транслитерация "authentik", смысловой перевод роли — identity/access
  guard); `pan.toml` `имя = "дозорный"`, экспортируемый модуль —
  `дозорный`.

## Итоги реализации (2026-08-21)

Все FR-001..FR-012 и SC-001..SC-006 реализованы и покрыты
`тест_дозорный.pns` (62 проверки, реальный сокет — запусти-спавненный
сервер на throwaway БД + panos-side HTTP-клиент, тот же паттерн, что
`test_приложение.pns` в быстряге). Файлы: `модель.pns` (SQLite-схема +
репозитории), `пароли.pns` (PBKDF2), `oauth.pns` (US1/US3, сырой
`http.Маршрутизатор`), `admin.pns` (US2, `быстряга.Приложение`, ПОЛНЫЙ
CRUD — create/read/update/delete для пользователей/групп/клиентов, не
только create+read, как в первой версии), `старт.pns` (сборка + FR-011
bootstrap).

**Реальные пробелы panos/быстряга, найденные и закрытые по ходу** (не
в `дозорный`, а в самих зависимостях — все закоммичены и запушены):
1. `криптография.случайные_байты_base64url` — CSPRNG, не был
   предвиден спекой, обнаружен как жёсткий блокер при первой попытке
   сгенерировать authorization code.
2. `Запрос.ответить_с_заголовками` — старый `ответить` не мог
   выставить `Location`/`Set-Cookie`, блокируя ЛЮБОЙ OAuth2-редирект.
3. `Маршрутизатор` полностью игнорировал query-строку —
   `?response_type=code&...` давал 404 на КАЖДЫЙ запрос с query,
   не только у дозорного.
4. `+` не декодировался как пробел в query/form (RFC 1866) —
   `scope=openid+profile` от настоящего `curl --data-urlencode`
   приходил одним словом.
5. быстряга: `отправить_пост_с`/`удалить_с`/`отправить_put_с`
   отсутствовали — POST/DELETE/PUT-обработчики не могли одновременно
   получить admin-auth-экстрактор, тело и (для PUT/DELETE) `:параметр`
   пути.
6. `ввод_вывод.печать` был полностью буферизован до выхода процесса —
   ломало живой лог ЛЮБОГО panos-сервера (`http.обслуживать` не
   возвращается на успехе), не только дозорного; FR-011 требует
   печать пароля в лог при старте.
7. Реальный, воспроизводимый баг тайпчекера (`inferGenericSubstitution`,
   `zig/core/type_checker.zig`) — cross-module generic-параметр с
   interface-bound не выводился, если аргумент — функция/замыкание из
   ДРУГОГО модуля; найден+исправлен в той же сессии (сравнение
   номинальных типов теперь учитывает `.identity`, как уже делали
   `assignable`/`TypeStore.eql`).
8. быстряга `получить`/`получить_с`/`удалить`/`удалить_с` всегда
   отвечали `200` (обработчик возвращал голый `Ответ`, не
   `Отклик(Ответ)`, как уже делали POST/PUT/DELETE) — `GET /api/
   пользователи/{несуществующий-id}` молча отвечал `200` с нулевыми
   полями вместо `404`. Ломающее изменение сигнатуры обработчика,
   принятое явным решением пользователя сессии — все существующие
   вызовы (`test_*.pns`, `quickstart.md`) обновлены.
9. `Ответ.заголовок(имя)` искал по нижнему регистру против
   НЕ-лоуеркейснутых заголовков — молча возвращал `Опция.Нет()` для
   ЛЮБОГО заголовка на реальном ответе (см. следующий пункт про
   редиректы, где это и обнаружилось).

**Ранее известный нюанс, ЗАКРЫТО**: клиентский `http.*` прозрачно
следует за 3xx-редиректами по умолчанию, без опции отказаться — сессия
изначально оставила это как есть (архитектурный вопрос, не решение с
ходу), `тест_дозорный.pns` обходил через сырой сокет для `/consent`.
Пользователь вернулся к вопросу и решил закрыть: новый core builtin
`сеть.http_запрос_без_редиректа` (`redirect_behavior=.unhandled`) +
`http.запросить_без_редиректа`/`отправить_пост_без_редиректа(_с_заголовками)`
— 3xx возвращается как есть. Сырой-сокет обход в `тест_дозорный.pns`
убран, заменён на `http.отправить_пост_без_редиректа`. Попутно найден и
исправлен ОТДЕЛЬНЫЙ реальный баг: `Ответ.заголовок(имя)` искал по
нижнему регистру против НЕ-лоуеркейснутых ключей заголовков (комментарий
про "native-клиент (external/odin-http)" в `пары_в_соответствие`
устарел — тот клиент убран Zig-миграцией, текущий `std.http.Client`
сохраняет регистр заголовков как на проводе) — `.заголовок("Location")`
молча возвращал `Опция.Нет()` для ЛЮБОГО ответа, не только редиректов.

**Не реализовано (сознательно, вне скоупа v1 — см. Assumptions)**: SAML,
LDAP/proxy outposts, визуальный flow/stage/policy-движок, admin SPA,
RBAC сверх admin/обычный пользователь, публичные клиенты (RS256/JWKS).
